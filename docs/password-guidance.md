# NIST and OWASP password guidance

This review uses [NIST SP 800-63B-4, §3.1.1.2 Password Verifiers](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver), its [password usability guidance](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordusability), the [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), and the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

NIST's SHALL requirements and SHOULD recommendations apply to verifiers/CSPs and the complete authentication system. OWASP supplies implementation guidance. This client-side package implements relevant password checks and UI examples; server policy, deployment, cryptography, and operational controls determine system-level conformance.

## Policy and implementation

| Topic                        | Current guidance                                                                                                                                                                                                         | Package or application behavior                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Minimum length               | NIST requires at least 15 characters for single-factor passwords. Passwords used only as part of MFA may use a minimum of 8. OWASP gives the same thresholds.                                                            | `LengthHandler` defaults to 15. An application choosing 8 must enforce MFA on the server; a checkbox or optional MFA setting is insufficient.                                                                                                                                                                                                                     |
| Maximum length               | NIST recommends, and OWASP calls for, accepting at least 64 characters. Reasonable input bounds can address denial of service.                                                                                           | The default UTF-8 limit is 1,024 bytes, enough for at least 64 characters even at four bytes per code point. Keep this capacity when choosing custom limits and enforce a server request limit.                                                                                                                                                                   |
| Unicode length               | NIST requires each Unicode code point to count as one character.                                                                                                                                                         | Count NFC-normalized code points, rather than UTF-16 code units. Emoji count as one code point each; a grapheme made from several code points counts accordingly.                                                                                                                                                                                                 |
| Unicode normalization        | NIST recommends NFC normalization before hashing Unicode password bytes.                                                                                                                                                 | The pipeline and built-in handlers use NFC. Server registration and login, and an OPAQUE implementation, must use the same canonicalization. Do not independently trim, case-fold, or truncate the authentication password.                                                                                                                                       |
| Character repertoire         | NIST recommends printing ASCII, spaces, and Unicode. OWASP calls for Unicode and whitespace without character-type restrictions.                                                                                         | No uppercase/lowercase/digit/symbol requirements or whitespace trimming. The samples use ordinary password inputs without `pattern`, `minlength`, or `maxlength` constraints that would count UTF-16 or truncate input.                                                                                                                                           |
| Complete-password blocklists | NIST requires screening common, expected, or compromised passwords at password establishment/change, comparing the entire password rather than its substrings. OWASP also recommends common/breached password screening. | Word and email-context handlers compare complete values. Regex blocklist patterns must match a complete value. Containing a listed word inside a longer passphrase is allowed. Use regexes only for known or expected blocked values, never composition requirements.                                                                                             |
| Breach screening             | A verifier needs a suitable common/compromised password blocklist. OWASP identifies Pwned Passwords as an option.                                                                                                        | The optional handler performs a SHA-1 range lookup on the complete NFC-normalized value. Only five hexadecimal prefix characters leave the client; padded responses are supported. Service, crypto, malformed-response, and empty-response errors reject the check. Production screening must also be enforced by the server or a trusted authentication service. |
| Rejection and guidance       | NIST requires the reason for a blocklist rejection and guidance to help the user choose a strong password. OWASP recommends a strength meter.                                                                            | Samples explain length/size/blocklist failures, recommend a different passphrase, and discourage trivial changes to a blocked value. Add a suitable local strength meter in the production UI; its score is guidance, not a substitute for policy or breach screening.                                                                                            |
| Password managers            | NIST requires password-manager/autofill support and recommends paste and a show-password option. OWASP calls for standard inputs and paste support.                                                                      | Samples use `autocomplete="new-password"`, allow paste, and provide a show/hide control. Displaying the value is an explicit local user choice; passwords are not placed in result output or logs.                                                                                                                                                                |
| Selection versus login       | NIST's blocklist requirement applies when establishing or changing passwords.                                                                                                                                            | Use the policy pipeline in those workflows. Login verifies the enrolled credential with the same normalization; it does not need to apply password-selection checks again.                                                                                                                                                                                        |

The samples' small local lists demonstrate the API. Turning off their optional remote check does not produce a comprehensive compromised-password check. A production verifier must select and maintain an adequate blocklist and enforce it independently of client controls.

## Pwned Passwords integration

OWASP's Authentication Cheat Sheet recommends Pwned Passwords for breached-password screening, using either its API or a locally hosted corpus. NIST requires a suitable common, expected, or compromised password blocklist; it does not mandate or endorse a particular provider.

The [official HIBP API documentation](https://haveibeenpwned.com/API/v3#PwnedPasswords) specifies `GET https://api.pwnedpasswords.com/range/{first 5 SHA-1 chars}`. The Pwned Passwords endpoint needs no API key or subscription. It differs from HIBP's email-breach lookup API. Hash the complete UTF-8 encoded password locally, send only the five-character prefix, and compare the returned 35-character suffixes locally. This package uses the same NFC-normalized value as its password policy. SHA-1 here is an API lookup identifier, not password storage or authentication cryptography.

Both samples request `Add-Padding: true`, ignore zero-count padding entries, and wait for submission before querying. HIBP warns against incremental searches as a user types, because a sequence of prefixes can reveal more about the password. HTTPS and response padding reduce disclosure, but the API infrastructure still receives the hash prefix and the requester's IP address; this is not a guarantee of anonymity. A server-side adapter or a maintained local corpus can avoid direct browser requests to HIBP.

Adapters must enforce a timeout and propagate HTTP failures. A failed, empty, or malformed lookup is an incomplete check, not evidence that the password is absent from the corpus. A successful lookup with no matching positive-count suffix means only that the password was not found in that corpus; it does not establish password strength or replace common/contextual blocklists and server enforcement.

## Server and authentication responsibilities

Use an authenticated protected channel (HTTPS/TLS) for password entry and authenticated sessions. NIST also requires rate limiting of failed account authentication attempts. Browser validation cannot enforce either server policy or account-level throttling. Implement appropriate MFA, safe recovery and reauthentication, generic login errors to reduce account enumeration, and session security at the application level.

NIST prohibits arbitrary periodic password changes, publicly accessible password hints, and knowledge-based security questions. Require a credential change when there is evidence of compromise. The package does not schedule password changes or supply hints/security questions.

For conventional server-side password verification, use a salted, adaptive password hashing scheme with a cost suited to the server. OWASP recommends Argon2id with at least 19 MiB of memory, two iterations, and parallelism one, or scrypt with `N = 2^17`, `r = 8`, `p = 1` when Argon2id is unavailable. Where FIPS-140 validation is required, OWASP recommends PBKDF2-HMAC-SHA-256 with at least 600,000 iterations and an appropriately validated implementation. Benchmark parameters under expected load. These are OWASP recommendations; NIST-approved scheme and validation requirements must be evaluated separately for the deployment. Do not use a fast SHA digest as the stored credential.

OPAQUE requires its own protocol implementation, configuration, registration records, server protections, and security review. Its credential storage follows the selected protocol rather than this package's policy-result format. Never store or transmit an OPAQUE session key through a `Result` password string. OPAQUE or any password-based mechanism must not be assumed to satisfy phishing resistance or a NIST assurance level solely because of its protocol name.

## Regression coverage

Automated checks cover single-factor length defaults, 64-character ASCII/Unicode/whitespace inputs, code-point counting, NFC consistency across validation/authentication/breach lookup, byte limits without truncation, complete-value word/email/regex comparisons, failure gating before authentication, Pwned Passwords padding and error handling, password visibility controls, rejection guidance, and both browser sample flows.
